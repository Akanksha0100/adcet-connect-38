# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Full-stack alumni engagement platform for ADCET. It is a **monorepo with two independent apps**:

- **Frontend** (repo root, `src/`) — Vite + React 18 + TypeScript SPA.
- **Backend** (`backend/`) — Express + Prisma + PostgreSQL REST API, versioned under `/api/v1`.

The two apps have **separate `package.json` files, separate dependencies, and separate test runners** (Vitest for frontend, Jest for backend). Run their commands from their respective directories.

## Commands

### Frontend (run from repo root)
```bash
npm run dev            # Vite dev server on http://localhost:8080
npm run build          # production build → dist/
npm run lint           # ESLint
npm test               # vitest run (all tests once)
npm run test:watch     # vitest in watch mode
npx vitest run src/path/to/file.test.tsx   # run a single test file
```

### Backend (run from `backend/`)
```bash
npm run dev            # tsx watch, loads .env.development, API on :4000
npm run build          # tsc → dist/
npm run seed           # idempotent dev seed (also places alumni on the map, offline)
npm run geo:backfill   # resolve cities the gazetteer didn't know (uses Nominatim)
npm run db:setup       # migrate (--name init) + seed
npm run db:reset       # reset DB + reseed (destructive)
npm run prisma:migrate # create + apply a dev migration
npm run prisma:studio  # browse data
npm test               # jest --runInBand (all tests)
npx jest src/tests/path/to/file.test.ts    # run a single test file
```

Backend npm scripts inject env via `dotenv -e .env.development`. Running `tsx`/`prisma` directly will **not** load env vars — use the npm scripts. Tests run under `NODE_ENV=test` with `--experimental-vm-modules` (ESM).

Both apps run at once in two terminals: backend on `:4000`, frontend on `:8080` (proxies to the API via `VITE_API_BASE_URL`). Swagger UI is at `http://localhost:4000/api/docs`.

## Backend architecture

**Modular monolith.** Every feature is a self-contained module in `backend/src/modules/<name>/` following a strict layered convention:

```
<name>.routes.ts       # Express router: mounts middleware chain + controllers
<name>.controller.ts   # thin HTTP layer: parse req → call service → send res
<name>.service.ts      # all business logic + Prisma calls live here
<name>.validators.ts   # Zod schemas for request bodies/queries
```

Adding a feature = create the module folder, then add one import + one `apiRouter.use(...)` line in `backend/src/routes/index.ts`. Modules never import each other's routers; shared logic goes in `backend/src/lib/`.

Key conventions:
- **App vs. server split**: `app.ts` is pure Express wiring (importable in tests, no `listen`); `server.ts` boots it and starts background cron jobs. Don't add business logic to either.
- **Middleware chain order** (see any `*.routes.ts`): `requireAuth` → `requireAdmin`/`requireRoles(...)` → `requireApproved` → `validate(schema, "query"|"body")` → `asyncHandler(ctrl.fn)`. All async controllers must be wrapped in `asyncHandler` so errors reach the global handler.
- **Errors**: throw the helpers from `lib/errors.ts` (`Unauthorized()`, `Forbidden()`, `NotFound()`, etc.) — never `res.status(...).json` for errors. `middlewares/errorHandler.ts` maps `ApiError`, `ZodError`, and Prisma errors (P2002→409, P2025→404) to responses centrally.
- **RBAC**: two roles (`ADMIN`, `ALUMNI`) stored in a **separate `UserRole` table**, not a column on `User`, to prevent privilege escalation. Use `requireRoles(...)` (OR semantics) or `isOwnerOrAdmin(req, ownerId)` from `middlewares/rbac.ts`. `STUDENT` and `RECRUITER` were dropped by migration `20260821090000_drop_student_recruiter_roles` — don't reintroduce them; `ROLE_VALUES` in `config/constants.ts` is the one list every role validator reads.
  - **A role is never read from client input.** `registerSchema` has no `role` field (Zod strips one that arrives, and `register()` hardcodes `ALUMNI`), `loginWithOAuth` does the same, and `updateProfileSchema`/`updateMeSchema` cannot touch roles or `status`. The only way to hold `ADMIN` is `POST /admin/users/:id/roles` — behind `requireAdmin` — or `seed-admin.ts` bootstrapping the first one. Tests in `tests/integration/auth.routes.test.ts` and `tests/integration/admin.routes.test.ts` pin all of this. Revoking a role also deletes that user's refresh tokens, so a demoted admin cannot mint a fresh token; `req.auth.roles` comes from the access token, so the demotion still takes up to `JWT_ACCESS_TTL` to be felt. An admin may not revoke their own `ADMIN` role — that is a lockout.
- **Links a user can store are `http(s)` only.** `z.string().url()` is `new URL()` underneath and accepts *any* scheme, so it happily stores `javascript:alert(1)` — which the frontend then renders as an `<a href>` on the public achievement page and in the admin's moderation queue. Every user-supplied link (`Achievement.link`, `Job.applyUrl`, `Event.meetingUrl`, `NewsItem.link`) validates with `httpUrl()` from `lib/urls.ts` instead; `src/lib/urls.ts` mirrors it as `safeExternalUrl()`, which every anchor built from stored data passes its URL through so rows written before the check are inert too. Never use `z.string().url()` for a user-supplied link again.
- **An upload key is not a capability.** `POST /uploads/presign-download` and `DELETE /uploads` take an object key from the request body, so `uploads.service.ts` authorises it: `parseObjectKey()` insists on the `<scope>/<ownerId>/<uuid>-<name>` shape (which also rejects `..` traversal), the private scopes `resume` and `receipt` are readable only by their owner, an admin, or — for a résumé — the alumnus who posted the job it was submitted to, and deleting is owner-or-admin always. `LocalStorage` re-checks that a resolved path stays inside the storage root.
- **CSV exports neutralise spreadsheet formulas.** Report columns carry names and companies members typed themselves, and the file opens on an admin's machine, so `csvCell` (backend `admin.service.ts`, mirrored by `src/lib/csv.ts`) prefixes a `'` to any cell starting with `= + - @` before quoting.
- **Pluggable storage**: `backend/src/storage/` has a `StorageService` interface with `LocalStorage` / `S3Storage` (MinIO in dev, S3 in prod) / `CloudinaryStorage` adapters, selected by `STORAGE_DRIVER` env var. Never call a provider SDK directly from modules — go through the storage service. Uploads are always browser → storage; `presignUpload()` returns either a `PUT` URL (S3 family) or `method: "POST"` + signed multipart `fields` (Cloudinary), and the frontend's `src/lib/upload.ts` handles both. `CloudinaryStorage` derives resource type and public id from the object key's extension; `src/lib/storage.ts` mirrors that mapping to build delivery URLs client-side — keep the two in sync.
- **Departments**: the 12 official ADCET department names live in `config/constants.ts` (`DEPARTMENTS`), mirrored verbatim by `src/lib/departments.ts` on the frontend — `src/tests/lib/departments.test.ts` fails if the two drift. Every **write** path (sign-up, profile PATCH, event, job) validates with `departmentSchema` / `optionalDepartmentSchema` from `lib/departments.ts`, so the column can never hold free text again; **read** filters use the lenient `departmentFilterSchema` so a stale value narrows results instead of 400ing. Frontend dropdowns render `DEPARTMENTS` (or `DEPARTMENT_FILTER_OPTIONS`, which prepends `"All"` — always strip `"All"` before sending). Migration `20260803093000_rename_departments` rewrote the old abbreviations and free-text spellings; don't reintroduce them.
- **Events and jobs target a *list* of departments**: `Event.departments` and `Job.departments` are `String[]`, validated by `departmentListSchema` (which de-dupes and drops the legacy `"All"` sentinel). **An empty array means everyone** — the same thing the old nullable `department` column meant by NULL. Within a list the departments OR together (`department: { in: [...] }`); read filters use `departments: { has: x }`, so postings open to all are deliberately *excluded* from a department-specific filter — it asks "aimed at X", not "visible to X". The UI is `src/components/DepartmentMultiSelect.tsx` (checkboxes), used by both create forms and both admin forms.
- **Sign-up requires a full profile**: `registerSchema` makes department, degree, graduation year, birthday, phone, city, current company and current role all mandatory alongside name/email/password/LinkedIn. Two things are deliberately *not* collected: the **admission year** (derived via `admissionYearFor(degree, graduationYear)` — B.E./B.Tech is 4 years, M.E./M.Tech is 2, from `DEGREES` in `config/constants.ts`) and the **birth year** (only `birthDay` + `birthMonth`, for birthday wishes). `DegreeType` has just `BE` and `ME`; PHD/DIPLOMA were dropped.
- **SSO never bypasses onboarding or approval**: `loginWithOAuth` creates new users **always PENDING** — a provider-verified email proves address ownership, not ADCET alumni status — with an empty profile. `publicUser` reports `profileComplete` (from `lib/profileCompletion.ts`), and the frontend's `ProtectedRoute` redirects anyone incomplete (admins excepted) to `/complete-profile`, which posts to `POST /auth/complete-profile`. That endpoint reuses the very same `requiredProfileFields` object as `registerSchema`, so an SSO user cannot skip a field form sign-up demands; a test asserts `REQUIRED_PROFILE_FIELDS` and that object stay in step. Completing a profile never changes approval status.
- **Emails are case-insensitive identities**: every email field flows through `emailSchema` in `auth.validators.ts`, which trims and lowercases at the validator boundary, and `loginWithOAuth` does the same to provider-supplied addresses. The DB has both a `User.email` unique constraint and a `lower(email)` unique index, and `register` catches P2002 as a 409 — the pre-flight lookup alone can't survive two concurrent sign-ups.
- **Donations are earmarked to a campaign**: `POST /donations/order` takes an optional `campaignId`, recorded on the `Donation` so the alumni office can see what each gift was given for (admin ledger has a "Given for" column, a campaign filter, and a per-campaign received breakdown). **Omitting it is valid** — that's a general-fund gift. `resolveCampaign()` in `donations.service.ts` rejects archived, not-yet-open and closed campaigns *before* any Razorpay order exists, so money is never pinned to a wound-up campaign; the donor-facing picker only lists ones currently open. Five campaigns ship in `seed.ts`.
  - **The public honour roll is derived, never curated.** `GET /donations/public/top-donors` (anonymous, `limit` capped at 24, 5-minute in-process cache dropped by `invalidateTopDonors()` whenever a gift settles or an admin moves its status) sums each donor's gifts and feeds `TopDonorsStrip` on the landing page. Three filters make it publishable and must stay: `status: "RECEIVED"` (a `PLEDGED` row is an unpaid order anyone can create — counting it would sell a place on the landing page for free), `isAnonymous: false` (the donor's own veto, applied retroactively because the total is recomputed every time), and `user: { status: "APPROVED" }`. Names, photos and batch come from `User`/`Profile` live, **not** from the frozen `donorName` snapshot the receipt uses, which is what makes the roll follow the alumni data. The section renders nothing at all when the list is empty.
- **Admin-tunable settings**: `backend/src/lib/settings.ts` holds a typed registry (key → Zod schema + default + label/description) and is the source of truth for **defaults**; the `AppSetting` table stores only overrides, so a missing row is normal and adding a setting needs no migration. Read with `getSetting(key)`, write with `setSettings({...}, adminId)`; a stored value that fails its schema is logged and falls back to the default. Exposed as `GET/PATCH /admin/settings`, which also returns `meta` so the admin UI renders labels without duplicating copy. Don't reach for `SiteSection` for settings — it survives only as a key/value store for the achievement authority recipients (`ACHIEVEMENT_RECIPIENTS_KEY`, edited from the admin Settings page) and its read endpoint is public.
- **Feed post quota**: members may publish `feedPostsPerMonth` (default 10) posts per **calendar month**, resetting on the 1st — a fixed reset day is far easier to explain than a rolling window. Admins are exempt. `feed.service.ts` exposes `getPostQuota()` (served at `GET /feed/quota`); `create` rejects with 429 when spent and returns the decremented `quota` alongside the post so the composer can toast "N posts left" without a second round trip.
  - **Usage lives in `PostQuotaUsage`, never in a count of `Post` rows.** The counter is append-only and keyed `(userId, "YYYY-MM")`: publishing spends the slot for that month *permanently*, so deleting the post does not hand it back and the cap can't be farmed by posting and deleting in a loop. `create` writes the post and the increment in one `$transaction` — a published post always costs a slot, and a slot is never spent without a post. Nothing in `remove` may touch the counter; a test asserts that.
- **Alumni Collaboration is a request board, not a scheduler** (`modules/collaboration/`): alumni offer to do something *for* the college — run a placement drive, conduct a workshop — and the office approves or rejects. Approving creates no `Event`, no `Job` and no calendar entry; it means "yes, let's talk", after which the office reaches the alumnus on the contact details captured in the request. Four rules:
  - **One table, one `type` discriminator.** Every kind shares the submit → PENDING → decision lifecycle, so `CollaborationRequest` holds the shared columns plus each kind's own nullable ones, and `collaboration.validators.ts` — *not* the schema — decides which are mandatory, via `z.discriminatedUnion("type", ...)`. Cross-field checks hang off the union with `.superRefine`, never off a member: `.refine()` turns a member into a `ZodEffects` that `discriminatedUnion` refuses. Adding the next kind is an enum value, a union member, its optional columns, and one entry in `COLLABORATION_KINDS`.
  - **Nothing here is public, at any status.** The whole router is `requireAuth + requireApproved`; a member reads and writes only their own requests (the service forces `userId` into the `where` for non-admins), and every decision route is `requireAdmin`. Approval never widens the audience — an approved drive is a private arrangement, not community content, which is the opposite of how achievements work.
  - **The frontend is written once and driven by `COLLABORATION_KINDS`** in `src/lib/collaboration.ts`: that record supplies each kind's slug, page copy and detail rows, and `CollaborationPage` / `CollaborationAdminPage` each take a `type` prop. The member page is a form on the left and the **Actions** panel on the right (their own requests with a status tag); the admin page is the same request rendered through the very same `RequestDetails` block, so the two sides cannot drift. Both sidebars render the kinds through `SidebarNavGroup`.
  - **Withdrawal stops at the decision.** A member may delete their own request only while it is `PENDING`; once decided, the row carries the reason they were told and deleting it would erase that. Admins may remove any request.
- **Newsroom is the only CMS**: the alumni office publishes two content types from `/admin/newsroom` (`src/pages/admin/NewsroomPage.tsx`) — `NewsItem` (public `/news` + `/dashboard/news`) and `Newsletter` (public `/newsletters`). Both live in `modules/content/` behind public GETs and admin-only writes; the frontend types and query factories are in `src/lib/newsroom.ts`. Two consequences:
  - **A newsletter carries its own cover.** `Newsletter.coverKey` is page 1 of `fileKey`, rasterised **in the admin's browser** by `src/lib/pdfCover.ts` when the PDF is picked, then uploaded under the `newsletter-cover` scope. No server-side rasteriser is required, and `pdfjs-dist` is reached only through that file's dynamic `import()` so it never lands in the public bundle. Both keys resolve through `assetUrl()` in `src/lib/storage.ts`, which passes `public/` paths straight through — that is how the two seeded editions (PDFs committed under `public/NewsLetter/`) coexist with uploaded ones.
  - **The old "Site Content" editor is gone**, along with `ResourceItem` and the `/dashboard/about|contact|mentorship|resources` pages: the public pages own that copy now. `src/lib/siteContent.ts` is down to fixed intro text for the two surviving in-portal pages (news, support). Don't reintroduce a section-copy editor.
- **Gallery is admin-managed** (`modules/gallery/`): `GalleryAlbum` (one event) has many `GalleryPhoto`. Public `GET /gallery/albums` is `optionalAuth` and returns published albums only — an admin passing `includeUnpublished=true` also sees drafts, which is why the controller re-checks `isAdmin(req)` instead of trusting the query. Photos are uploaded browser → storage under the `gallery` scope, then their keys are posted in one batch (`POST /gallery/albums/:id/photos`, appended after the existing `sortOrder`). Deleting an album or photo also deletes the stored object, except for keys starting with `/` — those are the seeded albums committed under `public/gallery/` and must never be deleted. Frontend types + mutations live in `src/lib/gallery.ts`; admin UI is `src/pages/admin/GalleryAdminPage.tsx`.
- **Directory search is name + company only**: `nameAndCompanyMatch()` in `alumni.service.ts` splits the query into words and ANDs them (so a full name narrows), each word ORing over first name, last name and employer. Department and graduation year are deliberately **not** searchable — they are multi-select filters instead, arriving as comma-separated `departments` / `graduationYears` query params (`csv()` in `alumni.validators.ts`) and applied as `{ in: [...] }`. The shared UI is `src/components/MultiSelectFilter.tsx`.
- **Chapter cards show a city photograph**, not a colour: `chapterImage()` in `src/lib/chapters.ts` maps slug/city → a file in `public/Chapters/` (both "bangalore" and "bengaluru" resolve). `Chapter.accent` survives only as the fallback header for a chapter with no photograph — there is deliberately no colour picker in the admin form any more.
- **The alumni map is DB-driven and clustered** (`modules/geo/`). Five rules hold it together:
  - **Coordinates live in the database, one row per city.** `GeoLocation` (unique `slug` = normalised `city|country`) is referenced by `Profile.locationId`. Nothing geocodes per request, and nothing geocodes per alumnus: 50,000 alumni in 200 cities cost 200 lookups. `GET /geo/public/map` (and its authenticated twin `GET /geo/map`, same payload) answers with three indexed aggregates plus one read of the small `GeoLocation` table, behind a 60-second in-process cache — call `invalidateMapCache()` after anything that rewrites coordinates.
  - **Resolution is gazetteer-first and never blocks a write.** `lib/geocode.ts` tries an existing row, then the offline `config/gazetteer.ts` (aliases included, so "Bangalore"/"Bengaluru" converge on one point and one row), and only then Nominatim — and only when the caller passes `allowRemote`, which `jobs/geoBackfill.ts` does and request paths never do. A city the gazetteer doesn't know leaves `locationId` null; the nightly backfill (or `npm run geo:backfill`) places it later, works per distinct city rather than per profile, and is idempotent. Adding a city to the gazetteer is an optimisation, never a requirement.
  - **City precision is the floor, by construction.** Only city + country are ever sent to a geocoder, only a centroid comes back, and `roundCoord` coarsens it to `GEO_PRECISION` (3 dp). There is no column that could hold a street address, and signing in buys no extra precision — a test asserts the anonymous and member payloads match.
  - **The map page is only the map.** No stat tiles, city index or country breakdown on `/alumni-map` or `/dashboard/geomap` — headcounts are on the markers, and the reporting lives in the admin Geo Map (`AdminGeoMapPage`). A test asserts the metrics stay off the public page.
  - **Clustering is supercluster, not markers-per-record.** `buildClusterIndex()` in `src/lib/geo.ts` weights clusters by the **summed headcount** via its `map`/`reduce` pair, so a marker reads "287 alumni" rather than supercluster's own `point_count` ("4 cities"). `src/components/public/AlumniMap.tsx` is only the Leaflet rendering half — it redraws the visible clusters on move/zoom and flies to `getClusterExpansionZoom()` on click. Don't reintroduce `leaflet.markercluster` or a hardcoded city→coordinate table (both were removed; the old `src/lib/city-coords.ts` is gone).
- **Background jobs**: `backend/src/jobs/` (event reminders, resume cleanup, geo backfill) are cron loops started in `server.ts` and stopped on graceful shutdown.
- **Email**: `lib/mailer.ts` + `lib/email-templates.ts` (branded HTML). Events/jobs send department-targeted emails; event emails contain token-signed RSVP links handled by the **public** `GET /events/:id/email-rsvp` endpoint (JWT in query params, no session).
- **Chapters** (`modules/chapters/`): regional alumni communities (Pune/Mumbai/Bangalore/Global seeded by migration + `DEFAULT_CHAPTERS` in `config/constants.ts`). Five rules the code depends on:
  - **Members read, admins write — with one exception.** `/dashboard/chapters` (`src/pages/ChaptersPage.tsx`) shows alumni the same chapter cards the admin sees and lets them click through to a chapter's roster; the only thing a member may change there is **their own answer to an invitation addressed to them** (the `MyInvitations` panel, from `GET /chapters/invitations/me` + `POST /chapters/invitations/:id/respond`). There is still no join, invite, edit, remove or archive control on it: every *other* mutating chapter route is `requireAdmin` and a test posts to each one as an approved member expecting 403, while the respond route re-checks the invitation's own `userId` and 403s anyone else's. `GET /chapters/:id/members` is the one route that widened: it is now `requireAuth + requireApproved`, and the controller passes `includeEmail: isAdmin(req)` so the email column is *not selected* for members — matching the alumni directory, which never returns one. Admins still manage everything under `/admin/chapters`.
  - **Display order is `Chapter.sortOrder`, not the alphabet** — the office wants Pune (1), Mumbai (2), Bangalore (3), Global (4). `list()` orders by `[isActive desc, sortOrder asc, name asc]` and every surface (public landing section, `/dashboard/chapters`, `/admin/chapters`) renders that one list without re-sorting, so the order is fixed in a single place. Chapters created later default to `sortOrder: 100` and fall in after the seeded four. `FALLBACK_CHAPTERS` in `src/lib/chapters.ts` must stay in the same order — it is what the public page renders when the API is unreachable. The **Global chapter** is the catch-all for alumni outside the three hubs; its `city` is deliberately NULL (it is not a place), so only its slug resolves `chapterImage()`, and the card omits the location line. It is created by migration `20260813051933_chapter_order_and_global`, not by `seed.ts`, because a deployed server only runs migrations plus `seed-admin.ts`.
  - **Invite-only membership** — there is deliberately no self-service join anywhere. An admin creates a `ChapterInvitation`; the alumnus becomes a member only when they accept. There are **two doors onto the same answer**, and both must keep working: the signed one-click links in the invitation email (public `GET /chapters/invitations/email-respond`, same token pattern as event RSVPs), and the pending-invitation panel on `/dashboard/chapters` (`POST /chapters/invitations/:id/respond`, session-authenticated). The portal door exists because an undelivered email used to strand an invitation forever — the invitee had a notification telling them to check an inbox and no way to act. Inviting must never grant membership — a test asserts this — so an admin still cannot add anyone unilaterally.
  - **One chapter per member** — membership is a single `Profile.chapterId`, not a join table, so accepting an invite repoints it and moves them out of any previous chapter (the email and confirm dialog say so). `updateProfileSchema` deliberately omits `chapterId` so it can't be set via a profile PATCH.
  - **Delete only while empty** — `DELETE /chapters/:id` succeeds only with zero members and zero events; otherwise it 409s and tells the admin to archive instead (`isActive: false`), which keeps members, events and history but hides the chapter and closes it to new invitations.
  - **Targeting is AND** — `Event.chapterId` and `Event.departments` are both optional narrowing filters on notifications, intersected (`{ department: { in: [...] }, chapterId }` on the profile relation). Chapter never affects event *visibility*, only who gets emailed. `jobs/eventReminders.ts` mirrors the same clause so reminders reach the same audience.

Prisma schema and `seed.ts` live in `backend/prisma/`. After changing `schema.prisma`, run `npm run prisma:migrate`.

## Frontend architecture

- **Routing** (`src/App.tsx`): all routes declared in one file. Three tiers:
  - Public routes (landing, login, static pages). `/login` and `/register` both render `AuthPage`, which picks its panel from `location.pathname` and mounts **only that one** — never both, at any breakpoint (a CSS-hidden second form would still expose duplicate email/password fields to screen readers and password managers). Public CTAs must match their wording: "Join Network" / "Get Started" → `/register`, "Sign In" → `/login`; `src/pages/auth-page.test.tsx` asserts this.
  - **The landing page runs in a fixed order**, asserted by `src/components/public/LandingSections.test.tsx`: founder → `LeadershipRow` (Secretary left, Joint Secretary right, driven by the ordered `LEADERSHIP` array in `src/lib/public-content.ts`) → director → `AlumniNetworkMessage` → board → chapters. The welcome message is long, so `AlumniNetworkMessage` renders only its **first** paragraph under `line-clamp-6` behind a Read more toggle. Clamp that one paragraph, never the container: `line-clamp` counts lines inside a single block, so clamping a wrapper of several `<p>`s cuts at a paragraph boundary instead of at six lines.
  - **Testimonials are one landing-page section with an overflow page behind it.** `TestimonialCard` (portrait left, name/batch/designation under it, quote right) is shared by the auto-advancing carousel in `TestimonialsSection` and by `/testimonials`, which renders the same card with `full`. The carousel shows an excerpt from `excerptOf()` — a word-boundary cut with a literal `...`, not a CSS line clamp, so every card is the same height — and the quote links through to the full page. `/testimonials` is deliberately **absent from the public nav**: the carousel is its only entry point, and a test asserts no such nav link exists.
  - `/complete-profile` — logged-in but outside `DashboardLayout`, so there is no nav to escape into until onboarding is done.
  - `/dashboard/*` — wrapped in `<ProtectedRoute>` (any logged-in role) → `<DashboardLayout>` → `<AccountStatusGate>` (blocks non-approved users).
  - `/admin/*` — wrapped in `<ProtectedRoute roles={["ADMIN"]}>` → `<AdminLayout>`.
  - **An achievement has two detail surfaces, and in-portal links must use the portal one.** `/dashboard/achievements/:id` (`AchievementDetailPage`) is a plain content block inside `DashboardLayout` — nav, sidebar and theme come from the layout, Back walks history and falls back to `/dashboard/achievements`, and it reads the authenticated `GET /achievements/:id` so an author can open their own *pending* submission. `/achievements/:id` (`PublicAchievementPage`) is the shareable twin for readers with no session: its own slim header, "Back to home", a sign-up CTA, and the anonymous `GET /achievements/public/:id` (published only). Both render `src/components/AchievementArticle.tsx`, so the achievement itself can't drift between them; only the surroundings differ. Cards in `AchievementsPage` link to the portal route, the landing page and the achievement emails link to the public one — pointing a portal card at `/achievements/:id` is the bug that made a click appear to leave the application, and `src/pages/AchievementDetailPage.test.tsx` now pins each side.
- **API client** (`src/lib/api.ts`): the single typed gateway to the backend. Framework-agnostic (no React imports). Persists JWTs in `localStorage` under `adcet.tokens`, auto-attaches the bearer token, and on 401 **transparently refreshes once and retries**. On hard auth failure it clears tokens and dispatches an `adcet:auth-expired` event that `AuthContext` listens for to sign out. Add new endpoints here rather than calling `fetch` from components.
- **State**: `AuthContext` (auth/session) and `ThemeContext` (5 themes + dark mode, persisted per-user in DB) in `src/contexts/`. Server state uses TanStack Query; there is no global store like Redux.
- **UI**: shadcn/ui components in `src/components/ui/` (generated — see `components.json`; regenerate rather than hand-editing). Styling is Tailwind. `@/` path alias maps to `src/`.
